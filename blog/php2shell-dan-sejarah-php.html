PHP2Shell Mengguncang Sebagian Besar Web, dan Sejarah PHP Menjelaskan Kenapa Itu Bisa Terjadi

Oleh I Putu Dicky Adi Pranatha • 23 Oktober 2026 • 12 min read • Frontend & Code
TL;DR / Ringkasan Cepat
  • Dua celah kritis tanpa autentikasi berjuluk PHP2Shell (CVE-2026-109618 dan CVE-2026-109619) dengan skor CVSS 9.2 menyerang langsung jantung interpreter PHP, bukan berkas kode aplikasi seperti WordPress atau Laravel.
  • Serangan dapat dieksekusi dari jarak jauh sebelum autentikasi atau logika aplikasi sempat berjalan, dengan risiko tertinggi menimpa server yang masih mengandalkan modul lawas Apache mod_php.
  • Satu-satunya solusi permanen adalah memperbarui instalasi ke versi patch resmi: PHP 8.5.12, 8.4.27, 8.3.36, atau 8.2.35.
  • Kerapuhan ini berakar dari keputusan kompromi desain memori dan filosofi praktis tanpa rancangan jangka panjang yang diwariskan sejak masa kelahiran PHP tiga puluh tahun lalu.

Dua celah keamanan berkategori kritis yang dinamai PHP2Shell resmi mengguncang infrastruktur web global pada tanggal 21 Oktober 2026. Celah ini memungkinkan penyerang tanpa hak akses mengambil alih kendali server secara penuh dari jarak jauh, bahkan sebelum satu baris pun kode aplikasi Anda sempat diproses. Mengingat PHP masih menggerakkan sekitar 69 persen dari seluruh situs web di dunia yang bahasa backend-nya terdata oleh W3Techs, insiden ini bukan sekadar insiden keamanan biasa, melainkan ujian terberat bagi ketahanan ekosistem web modern.

Banyak pengembang keliru mengira bahwa selama mereka menggunakan kerangka kerja modern, menerapkan filter input yang ketat, dan mematikan fungsi berbahaya seperti eval(), server mereka akan otomatis aman. Kerentanan kali ini membuktikan sebaliknya. Masalahnya tidak terletak pada kualitas penulisan kode PHP buatan Anda, melainkan pada mesin eksekusi C di balik layar yang menerjemahkan kode tersebut. Untuk memahami mengapa krisis sebesar ini bisa terjadi pada perangkat lunak yang telah berusia tiga puluh tahun, kita perlu membedah anatomi celahnya, menelusuri bagaimana celah tersebut terbongkar, dan membaca kembali sejarah panjang keputusan desain PHP sejak era Personal Home Page Tools.

Satu Permintaan Tanpa Login Cukup untuk Mengambil Alih Server

Skenario terburuk dalam dunia keamanan siber adalah celah eksekusi kode jarak jauh tanpa autentikasi (*unauthenticated remote code execution*). Dalam skenario ini, penyerang tidak memerlukan nama pengguna, kata sandi, token API, maupun sesi login yang sah. Mereka cukup mengirimkan satu paket permintaan HTTP yang dirancang khusus ke alamat web publik Anda. Ketika server menerima permintaan tersebut, interpreter PHP akan mengalami kegagalan internal yang dapat dimanipulasi untuk menjalankan perintah sistem operasi dengan hak akses proses web server.

Situasi ini menempatkan tim operasional sistem dan pemilik situs web dalam kondisi siaga darurat. Lapisan perlindungan aplikasi yang umum dipasang, seperti sistem autentikasi dua faktor, gerbang login administrator, atau validasi formulir berlapis, menjadi tidak berdaya karena penyerang menyerang di level mesin sebelum lapisan logika aplikasi tersebut sempat dibangun di memori.

Dua Celah di Mesin PHP, Bukan di Kode Aplikasimu

Krisis PHP2Shell berpusat pada dua nomor identifikasi kerentanan resmi yang diterbitkan oleh tim keamanan PHP:

  1. CVE-2026-109618 (Kerusakan Memori Akibat Batas Alokasi): Ketika PHP menerima data masukan berukuran besar, misalnya berkas unggahan atau formulir multipart, PHP memantau batas penggunaan memori yang ditetapkan oleh arahan memory_limit. Jika alokasi melampaui batas tersebut, mesin Zend Engine memicu mekanisme penghentian darurat internal bernama zend_bailout() yang memanfaatkan fungsi bahasa C longjmp() untuk memotong eksekusi secara mendadak. Masalahnya, pemotongan mendadak ini bisa terjadi ketika struktur data internal baru separuh terbentuk. Saat proses pembersihan memori (*request shutdown*) berjalan, interpreter keliru mengira struktur data yang rusak itu valid, lalu mencoba membebaskan pointer yang tidak sah sehingga membuka celah kerusakan memori (*use-after-free*) yang dapat diarahkan menuju eksekusi kode.
  2. CVE-2026-109619 (Kondisi State Global Usang): Arsitektur PHP bekerja dengan siklus worker yang melayani permintaan secara berulang untuk menghemat beban inisialisasi proses. Pada kondisi kesalahan fatal atau interupsi tertentu, pointer internal global milik sistem dapat tertinggal dan tetap menunjuk ke blok memori dari permintaan sebelumnya yang sebenarnya sudah dihapus. Ketika permintaan berikutnya masuk dan diproses oleh worker yang sama, interpreter dapat membaca atau mengeksekusi sisa referensi usang tersebut sebelum proses inisialisasi normal sempat membersihkannya. Vektor ini tidak hanya membuka celah pengambilalihan proses, tetapi juga berpotensi membocorkan data sensitif seperti token rahasia dan kunci enkripsi antar-sesi pengguna.

Kedua kerentanan ini diberi skor keparahan resmi 9.2 pada skala CVSS v4.0. Meskipun beberapa laporan awal di komunitas sempat membulatkannya menjadi 10.0 karena dampak luasnya, angka 9.2 tetap menempatkan PHP2Shell pada tingkat keparahan luar biasa yang menuntut penanganan langsung tanpa penundaan.

Kenapa mod_php Berada di Barisan Paling Rawan

Tingkat risiko yang dihadapi setiap server sangat bergantung pada antarmuka penghubung server web yang digunakan (*Server Application Programming Interface* atau SAPI). Dokumentasi resmi tim keamanan PHP menegaskan bahwa seluruh lingkungan yang memproses permintaan web terdampak, termasuk PHP-FPM, php-cgi, FrankenPHP, LiteSpeed, dan Apache dengan modul mod_php.

Namun, risiko tertinggi berada di pundak server yang masih menjalankan mod_php. Pada arsitektur modul lawas ini, interpreter PHP tertanam langsung di dalam proses inti web server Apache. Prosedur pembersihan permintaan pada mod_php dipanggil tanpa syarat, bahkan jika tahap inisialisasi permintaan gagal total sejak byte pertama. Artinya, penyerang memiliki jalur eksploitasi terdemonstrasi yang stabil dan dapat dipicu tanpa hambatan lapisan isolasi apa pun.

Bagaimana Celah Ini Ditemukan Sebelum Penyerang Sempat Menemukannya

Menemukan kesalahan logika alokasi memori di dalam jutaan baris kode sumber bahasa C bukanlah pekerjaan mudah. Bug ini bukan kesalahan sintaksis biasa yang bisa ditangkap oleh *linter*, melainkan kondisi balapan mikro (*micro-race condition*) pada saat penanganan galat ekstrim. Penemuan celah ini menyingkap babak baru dalam metodologi audit keamanan perangkat lunak fondasional internet.

Keberhasilan mitigasi sebelum terjadi gelombang eksploitasi massal yang merata adalah hasil dari kolaborasi terencana antara konsorsium nirlaba, peneliti keamanan independen, dan teknologi audit berbantuan kecerdasan buatan modern.

Audit Berbantuan AI yang Membongkar Bug Lama

Akar penemuan PHP2Shell bermula ketika PHP bergabung dalam program inisiatif keamanan sumber terbuka *Patch the Planet*, sebuah gerakan kolaboratif yang didukung oleh The PHP Foundation untuk memperkuat audit perangkat lunak vital internet. Pada tanggal 30 Juli 2026, firma riset keamanan Calif memulai audit mendalam terhadap basis kode inti PHP menggunakan model penalaran AI tingkat lanjut.

Peneliti Ryan A dari Calif meninjau kembali pola anomali alokasi memori yang pernah dicatat samar-samar pada tahun 2024. Melalui pengujian terarah terhadap perilaku zend_bailout(), mereka berhasil merekonstruksi kondisi di mana kegagalan alokasi memori dapat dimanfaatkan untuk membajak pointer kontrol proses. Tak lama berselang, peneliti dari Wiz pada tanggal 24 Agustus serta tim OpenAI pada tanggal 18 September secara independen menemukan dan melaporkan vektor serangan tambahan yang saling bersilangan pada komponen state global. Rangkaian temuan ini membuktikan bahwa masalah alokasi memori tersebut merupakan cacat kelas arsitektur yang sudah mengendap lama di jantung interpreter.

Embargo yang Bocor Sehari Lebih Cepat

Dalam protokol koordinasi keamanan siber yang sehat, penemuan celah disimpan di bawah status embargo ketat. Peneliti dan pengembang inti bekerja secara tertutup untuk menyiapkan tambalan kode, menguji kompatibilitas, serta membagikan draf perbaikan kepada penyedia distribusi Linux besar seperti Debian, Ubuntu, dan Red Hat agar paket pembaruan dapat dirilis serentak.

Rencana jadwal rilis resmi awalnya dipatok pada hari Kamis, 22 Oktober 2026. Namun, pada Selasa tanggal 20 Oktober sekitar pukul 15.00 UTC, dinding kerahasiaan tersebut retak. Nomor identifikasi CVE beserta spekulasi teknis mengenai celah eksekusi kode interpreter mulai bocor di forum publik Hacker News dan media sosial. Menghadapi situasi genting di mana komunitas pengembang mulai panik dan aktor ancaman berpotensi merekayasa balik celah tersebut dari rumor yang beredar, The PHP Foundation mengambil keputusan cepat. Mereka memajukan pra-pengumuman pada malam harinya dan merilis paket pembaruan darurat pada Rabu, 21 Oktober 2026 pukul 14.00 UTC, sehari lebih awal dari rencana semula.

Konsekuensi yang Terasa dari Server Pribadi sampai Hosting Bersama

Dampak dari kebocoran embargo dan rilis darurat ini langsung menjalar ke seluruh penjuru internet. Dari pengembang yang mengelola server virtual pribadi (VPS), insinyur keandalan situs di perusahaan teknologi, hingga pemilik usaha mikro yang menyewa layanan *shared hosting* murah, semua menghadapi realitas yang sama: memperbarui versi atau menghadapi risiko intrusi.

Namun, kemudahan melakukan pembaruan tidak terdistribusi secara merata di dunia nyata. Di sinilah jurang teknis antara arsitektur modern dan sistem warisan (*legacy systems*) berubah menjadi krisis operasional.

Lingkungan Server Versi PHP Terpasang Tingkat Risiko Tindakan Wajib yang Harus Diambil
Server Modern (PHP-FPM / FrankenPHP) PHP 8.2, 8.3, 8.4, atau 8.5 Tinggi jika belum ditambal Perbarui paket ke 8.2.35, 8.3.36, 8.4.27, atau 8.5.12 melalui package manager sistem operasi hari ini.

Situs Hosting Bersama (Shared Hosting) Ditentukan oleh pengelola hosting Tergantung kecepatan host Periksa versi PHP aktif di cPanel. Jika masih versi lama, minta pengelola memperbarui runtime atau ubah selector versi.

Versi Lama yang Kini Tidak Punya Pelindung

Masalah paling pelik dalam ekosistem web adalah keberadaan jutaan instalasi PHP versi lawas yang sudah lama melewati masa akhir dukungan (*End of Life* / EOL). Berdasarkan kebijakan resmi proyek PHP, setiap versi minor hanya mendapatkan dukungan aktif selama dua tahun dan perbaikan keamanan selama dua tahun tambahan. Versi populer seperti PHP 7.4, 8.0, dan 8.1 sudah bertahun-tahun tidak menerima pembaruan resmi dari komunitas inti.

Banyak pemilik situs enggan memperbarui versi karena khawatir kode plugin lawas mereka rusak atau tidak kompatibel dengan standar PHP 8. Menyadari risiko bencana global jika versi lama dibiarkan telanjang, tim keamanan PHP mengambil langkah luar biasa dengan menyediakan cabang *backport* kode sumber minimal untuk cabang 7.4, 8.0, dan 8.1 di repositori GitHub mereka. Langkah darurat ini sangat menolong penyedia Linux enterprise dan pengembang yang mengompilasi biner secara mandiri, tetapi tidak otomatis menolong pengguna shared hosting biasa jika pengelola server mereka lambat bertindak.

Mitigasi Sementara yang Sering Disalahpahami

Bagi administrator yang belum dapat melakukan pembaruan biner saat ini juga, tim keamanan PHP merilis sejumlah rekomendasi konfigurasi sementara. Namun, ada banyak salah kaprah di kalangan pengembang yang justru memberikan rasa aman palsu.

Menyembunyikan pesan kesalahan dengan menyetel display_errors = Off atau membungkam ekspresi menggunakan operator @ sama sekali tidak melindungi sistem Anda. Celah ini terjadi di level interpretasi memori C saat pembersihan fatal error, bukan saat teks galat dicetak ke layar peramban. Begitu pula anggapan bahwa arahan ini_set() di awal berkas index aplikasi dapat menangkal serangan; penyerang memicu kerentanan sebelum parser sempat mengeksekusi fungsi tersebut.

Konfigurasi mitigasi sementara yang sah harus disuntikkan langsung di berkas php.ini global atau konfigurasi pool PHP-FPM sebelum pemrosesan permintaan dimulai: 

; Mitigasi Sementara PHP2Shell di php.ini atau FPM pool
; 1. Mengurangi risiko jalur OOM pada berkas unggahan
post_max_size = 8M
upload_max_filesize = 8M

; 2. Menutup jalur eksploitasi status global sesi (CVE-2026-109619)
session.upload_progress.enabled = 0

; 3. Khusus PHP 8.5: matikan pelacakan galat fatal
fatal_error_backtraces = 0

Mitigasi di atas hanya mempersempit jalur serangan yang telah terkonfirmasi, bukan menghilangkan kerentanan secara tuntas. Pembaruan biner interpreter tetap menjadi satu-satunya pelindung mutlak.

Dari Personal Home Page ke Penggerak Mayoritas Web

Pertanyaan mendasar yang wajar muncul di benak setiap praktisi teknologi adalah: bagaimana mungkin sebuah bahasa pemrograman yang menopang triliunan transaksi ekonomi digital dunia memiliki arsitektur manajemen memori yang bisa dibajak melalui interupsi alokasi sederhana? Jawabannya tidak ditemukan di buku teks teori komputer modern, melainkan pada DNA kelahiran PHP tiga puluh tahun silam.

PHP tidak pernah dirancang di laboratorium riset universitas bergengsi atau dibangun oleh komite insinyur korporasi besar seperti Java atau C#. PHP lahir sebagai serangkaian alat bantu praktis untuk menyelesaikan masalah mendesak seorang pemrogram web di era awal internet.

Skrip Pencatat Pengunjung yang Tidak Dirancang untuk Bertahan Lama

Pada tahun 1994, seorang pemrogram berdarah Denmark-Kanada bernama Rasmus Lerdorf ingin memantau siapa saja yang membaca kurikulum vitae daring dan halaman portofolio pribadinya. Untuk keperluan sederhana itu, Rasmus menulis sekumpulan biner CGI kecil menggunakan bahasa pemrograman C. Kumpulan alat kecil ini ia beri nama Personal Home Page Tools (PHP Tools).

Sering ada miskonsepsi umum di berbagai artikel daring yang menyebutkan bahwa versi awal PHP ditulis menggunakan bahasa Perl. Dokumentasi sejarah resmi php.net mengklarifikasi bahwa biner CGI tersebut sejak awal ditulis oleh Rasmus menggunakan bahasa C. Pada pertengahan tahun 1995, Rasmus merilis kode sumber tersebut ke publik dengan nama PHP/FI (Personal Home Page / Forms Interpreter). Versi ini sudah dilengkapi kemampuan dasar untuk memproses data formulir HTML dan berkomunikasi dengan basis data sederhana seperti mSQL.

Filosofi Rasmus saat itu sangat pragmatis: ia tidak berniat menciptakan bahasa pemrograman baru. Ia hanya ingin alat yang membuat halaman web statis menjadi dinamis dengan usaha sekecil mungkin. Jika sebuah skrip mengalami galat atau kehabisan memori, pendekatan paling logis pada era CGI adalah mematikan proses tersebut secepat mungkin dan membiarkan sistem operasi membersihkan sisanya. Asumsi dasar ini bekerja sempurna untuk situs pribadi dengan puluhan pengunjung per hari, tetapi menjadi bom waktu ketika PHP berevolusi menjadi pelayan jutaan permintaan konkuren per detik.

Zend Engine dan Keputusan Desain yang Masih Hidup Hingga Hari Ini

Titik balik peradaban PHP terjadi pada tahun 1997. Dua mahasiswa Technion di Israel, Andi Gutmans dan Zeev Suraski, mencoba membangun proyek toko daring komersial menggunakan PHP/FI 2.0. Mereka segera menyadari bahwa arsitektur yang dirancang Rasmus tidak sanggup menopang logika bisnis yang rumit dan transaksi bernilai tinggi.

Alih-alih meninggalkan PHP, Andi dan Zeev memutuskan untuk menulis ulang mesin parser interpreter dari nol. Mereka bekerja sama dengan Rasmus untuk melahirkan PHP 3.0 pada Juni 1998. Pada momentum inilah akronim PHP diubah menjadi singkatan rekursif yang kita kenal sekarang: PHP: Hypertext Preprocessor. Keberhasilan PHP 3 mendorong Andi dan Zeev merancang mesin eksekusi generasi baru bernama Zend Engine (gabungan nama Zeev dan Andi) yang menjadi fondasi utama peluncuran PHP 4.0 pada tahun 2000.

Zend Engine memperkenalkan model eksekusi *shared-nothing*. Dalam filosofi ini, setiap permintaan web diperlakukan sebagai entitas yang terisolasi total: memori dialokasikan saat permintaan datang, kode dieksekusi, keluaran HTML dikirimkan ke peramban, lalu seluruh memori dibersihkan dalam sekejap. Pengembang web menyukai model ini karena mereka tidak perlu pusing memikirkan kebocoran memori jangka panjang (*memory leaks*) seperti yang dihadapi pengembang Java atau C++. Jika terjadi galat fatal, mesin cukup memanggil longjmp() untuk memutus alur kerja secara paksa. Namun, keputusan untuk mengorbankan penanganan unwinding memori yang ketat demi kecepatan eksekusi inilah yang puluhan tahun kemudian menjadi fondasi hadirnya CVE-2026-109618.

Pola Lama yang Terus Berulang dalam Sejarah Keamanan PHP

Melihat ke belakang, insiden PHP2Shell bukan kali pertama ekosistem PHP diguncang krisis keamanan berskala global. Ada pola historis yang konsisten dalam evolusi bahasa ini: ketegangan antara kemudahan pemakaian bagi pemula (*developer ergonomics*) melawan prinsip keamanan perangkat lunak yang ketat (*defensive engineering*).

Setiap lompatan besar dalam sejarah PHP hampir selalu dipicu oleh keberanian komunitas untuk membuang fitur-fitur lama yang terbukti menjadi pintu masuk eksploitasi massal.

Era Konfigurasi yang Terlalu Percaya pada Input Pengguna

Bagi mereka yang membangun web di era 2000-an awal bersama PHP 4 dan rilis awal PHP 5, fitur bernama register_globals adalah kenangan buruk yang sulit dilupakan. Demi mempermudah pemula membaca parameter URL atau formulir, fitur ini secara otomatis mengubah setiap parameter HTTP GET dan POST menjadi variabel global di dalam skrip. Parameter ?admin=1 di bilah peramban secara otomatis menciptakan variabel $admin = 1 di dalam kode. Celah otorisasi massal pun meledak di ribuan situs web di seluruh dunia.

Dibutuhkan waktu bertahun-tahun bagi komunitas untuk menonaktifkan fitur tersebut secara bawaan dan akhirnya menghapusnya secara permanen di PHP 5.4. Pola serupa terjadi pada fitur magic_quotes_gpc dan mode operasi *safe mode*, fitur-fitur tambal sulam yang berusaha melindungi pemrogram ceroboh dari serangan injeksi SQL, tetapi justru melahirkan kerentanan baru dan mengaburkan pemahaman tentang sanitasi data yang benar.

Ketika Celah Tahun 2012 Bangkit Lagi di Tahun 2024

Bukti lain bahwa keputusan desain masa lalu terus membayangi masa kini adalah insiden CVE-2024-4577 yang diungkap oleh peneliti ternama Orange Tsai dari DEVCORE pada pertengahan tahun 2024. Celah tersebut merupakan kerentanan injeksi argumen pada implementasi PHP-CGI di sistem operasi Windows.

Yang mengejutkan, celah tahun 2024 tersebut adalah turunan langsung dari kerentanan lama CVE-2012-1823 yang telah ditambal dua belas tahun sebelumnya. Perubahan penanganan set karakter multibyte pada sistem operasi modern membuka kembali pintu lama yang disangka sudah terkunci rapat. Sejarah membuktikan bahwa bug di level arsitektur interpreter tidak pernah benar-benar mati; mereka hanya tertidur menunggu perubahan lingkungan sistem operasi membangunkannya kembali.

PHP 7, PHP 8, dan Upaya Panjang Menebus Reputasi

Terlepas dari beban sejarah masa lalunya, tidak adil jika kita menilai PHP hari ini hanya dari lensa kegagalan masa lalu. Sepuluh tahun terakhir adalah periode modernisasi paling agresif dan mengagumkan dalam sejarah bahasa pemrograman sumber terbuka.

Peluncuran PHP 7.0 pada tahun 2015 mematahkan stigma bahwa PHP adalah bahasa yang lambat dan boros sumber daya. Melalui perombakan total struktur data internal dalam proyek PHPNG, PHP 7 menggandakan kecepatan eksekusi dan memangkas separuh konsumsi memori, menyelamatkan jutaan server dari kebutuhan penambahan perangkat keras yang mahal. Komunitas bahkan sengaja melompati nomor versi 6 untuk menjaga integritas teknis setelah proyek PHP 6 berbasis Unicode mandek di tengah jalan.

Modernisasi berlanjut lebih solid di era PHP 8 yang dimulai pada akhir 2020. PHP berevolusi menjadi bahasa modern yang kaya fitur: sistem pengetikan ketat (*strict typing*), kompilator Just-In-Time (JIT), atribut kelas terstruktur, *match expressions*, hingga penanganan galat yang jauh lebih disiplin. Pembentukan The PHP Foundation pada akhir 2021 oleh koalisi perusahaan teknologi besar seperti JetBrains, Automattic, Laravel, dan Acquia memastikan pendanaan penuh bagi pengembang inti untuk bekerja secara profesional merawat infrastruktur bahasa. Kehadiran program audit AI seperti *Patch the Planet* adalah buah nyata dari profesionalisasi tata kelola ini; celah PHP2Shell ditemukan dan ditambal oleh tim internal sebelum penyerang sempat memanfaatkannya secara luas di lapangan.

Memeriksa Servermu Hari Ini dan Membaca PHP dengan Kacamata yang Lebih Jujur

Sebagai penutup yang menuntut aksi nyata, hal pertama yang wajib Anda lakukan setelah menyelesaikan artikel ini adalah membuka terminal server Anda dan memastikan status keamanan instalasi PHP Anda. Jangan menunda hingga esok hari, karena pemindaian otomatis oleh bot penyerang di jaringan internet global tidak pernah mengenal hari libur.

Jalankan perintah berikut pada baris perintah server Anda: 

# 1. Periksa nomor versi biner PHP aktif
php -v

# 2. Periksa jenis SAPI yang sedang berjalan
php -i | grep "Server API"

Jika keluaran versi menampilkan nomor di bawah PHP 8.2.35, 8.3.36, 8.4.27, atau 8.5.12, segera jalankan pembaruan melalui manajer paket distribusi Linux Anda (seperti apt update && apt upgrade atau dnf update), lalu lakukan restart pada layanan php-fpm atau apache2 Anda.

Insiden PHP2Shell memberi kita pelajaran berharga tentang ekosistem perangkat lunak dunia: tidak ada bahasa pemrograman yang sempurna, dan tidak ada teknologi yang kebal dari kesalahan masa lalunya. Kerapuhan di batas antara logika bahasa tingkat tinggi dan kode C sistem ini juga terlihat pada runtime lain di era modern, sebagaimana yang kami bedah dalam analisis mendalam Node2Shell dan celah decoder Brotli pada Node.js. Menghakimi PHP hanya dari kerentanan ini sama kelirunya dengan memuji PHP secara buta tanpa memahami kompromi teknis di balik mesinnya. PHP bertahan menopang mayoritas web selama tiga puluh tahun bukan karena ia dirancang tanpa cela, melainkan karena ia selalu memiliki komunitas tangguh yang bersedia mengakui kelemahan, merombak fondasi yang rapuh, dan terus melangkah maju merawat web yang kita gunakan bersama setiap hari.
